## Completed declarative query authoring lineage retained for context

The material below is completed historical context. Old SwifQL module/path/API spellings inside this lineage describe the repository state when those artifacts and commits were produced; they are not current package/module guidance.

Historical accepted direction included:

- SQL-first clause-local result builders rather than a parallel query AST or renderer;
- the existing parts/preparation/binding engine remains primary;
- multi-item clauses should prefer readable closure forms where they materially improve composition, with concise argument forms retained for one/few simple items;
- `Where { ... }` default AND composition plus explicit grouped `And { ... }` / `Or { ... }` is stable design under `DESIGN-020`;
- runtime `if` / optional branches / loops are allowed where SQL grammar permits omission, without synthetic fallback SQL;
- exact Swift -> SQL examples are mandatory for every proposed DSL form, with prepared SQL/value order when relevant;
- design coverage priority is PostgreSQL first, Duck next, MySQL third, while shared internals still obey the cross-dialect architecture gate;
- existing raw/fluent SwifQL remains compatibility surface during this wave unless a separately accepted major-version breaking migration is recorded;
- aggregate-argument ownership is now stable design under `DESIGN-025`: aggregate helpers may gain builder overloads where direct arguments, plain aggregate `DISTINCT`, and aggregate-local `ORDER BY` stay inside the function call, while `WITHIN GROUP`, `FILTER`, `OVER`, SELECT `DISTINCT`, and `DISTINCT ON` retain separate SQL ownership;
- Expression Frontier 01 is architecture-complete under `DESIGN-025` and final `DESIGN-026`: SQL ARRAY uses grammar-role members on the real Swift type (`Array.items(...)` / `Array.items { ... }` for `ARRAY[...]`, `Array.subquery(...)` / `Array.subquery { ... }` for `ARRAY(subquery)`); quantified comparisons use exceptional exact-SQL uppercase `ANY` only for the Swift `Any` collision, while non-conflicting `All` and `Some` retain normal SwifQL casing. All exact call sites are compiler-validated across Swift 6.2.3, Xcode/Swiftly 6.3.3, and Swift 6.4. Slices use structural `slice(...)`; DuckDB v1.5.5 quantified/ordered-set/hypothetical-set/FILTER/DISTINCT+ORDER BY capability boundaries are native-resolved; collection `&&`/`||` intentionally keep literal raw-operator composition rather than a misleading semantic alias. `QUERY-RB-019` remains only for eventual generic custom-aggregate implementation/extensibility planning and does not block Expression Frontier 02.

The target design inventory must cover the major SELECT/expression/DML grammar families before implementation is frozen, including multi-item SELECT/FROM/GROUP/ORDER forms, aliases, DISTINCT/DISTINCT ON, joins and lateral subqueries, predicates/subqueries/EXISTS/IN, grouping sets, windows/OVER/QUALIFY, set operations, WITH/recursive WITH, sampling, pagination/FETCH, row locking, and the important PostgreSQL-first expression families. Proposed syntax that is still under discussion belongs in `OPEN_DECISIONS.md`, not here.

Expression Frontier 02 is architecture-complete under final `DESIGN-027`. Stable architecture covers: separation of JSON navigation / symbolic JSON operators / SQL-JSON query-function grammar; no fake cross-dialect `JSONPath` type; structural `JSONExists` / `JSONQuery` / `JSONValue` ownership where exact identity is verified; compiler-validated direct trailing option builders and exact SQL/JSON option vocabulary; contextual SQL/JSON path argument rendering where a dialect requires a parser literal; always-grouped exact binary `.op(.custom(...), rhs)`; postfix/inline `Collate`, `AtTimeZone`, and PostgreSQL `AtLocal`; and stable PostgreSQL range/multirange `Fn` / `Type` / operator inventory. Named punctuation `Op` constants are closed negatively; `.op(.custom(token), rhs)` remains the exact escape. `JSON_TABLE` is explicitly deferred to the later typed record/table-function frontier under `QUERY-RB-014`.

Frontier 02 does not authorize production implementation.

Structural Continuation Frontier 03 is architecture-complete under `DESIGN-028`. This closes `QUERY-RB-011`, `QUERY-RB-002`, and `QUERY-RB-012`. Production implementation remains unauthorized.

SELECT / Set-Result Frontier 04 is architecture-complete under `DESIGN-029` and `DESIGN-030`. `QUERY-RB-001` and `QUERY-RB-007` are closed. Exact overload/coexistence behavior still requires fresh imported-module feasibility evidence before implementation. Production implementation remains unauthorized.

Statement Tail Frontier 05 is architecture-complete under `DESIGN-031` and `DESIGN-032`. `QUERY-RB-004` and `QUERY-RB-005` are closed.
