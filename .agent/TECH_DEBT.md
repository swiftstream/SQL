# Verified Technical Debt

Only evidence-backed debt belongs here. Do not treat an entry as permission to change code outside an approved implementation scope.

This is stable documentation. Every debt entry must be self-contained and durable: do not link to or depend on transient execution reports, temporary prompts, disposable diagnostics, or any other non-stable work product. Stable debt must describe its own scope, evidence requirement, and closure condition directly; transient work products may reference the stable debt owner, never the reverse.

1. **Unknown part dispatch omission** - `prepare(_:)` currently falls through to empty-string rendering for an unknown or unhandled `SwifQLPart`. A new part can therefore be silently omitted if dispatch support is forgotten. This remains verified debt and is not fixed by governance or render scopes.

2. **External `SQLDialect` subclass construction gap** - CLOSED for the audited extension path. An external consumer fixture proved that a downstream module can construct a custom `SQLDialect` subclass and use the additive context-aware rendering hook; `SQLDialect.init()` is public and the established hook remains the default forwarding boundary. Future extension surfaces still require focused external compile coverage.

3. **Generic SQL `name := expression` API is intentionally deferred** - Duck STRUCT/UNION construction/update and macro default/named-call grammar can require `:=`, while table-function options use the distinct `name = value` grammar. The maintainer explicitly deferred a generic public named-argument abstraction from the current Duck closure. Do not improvise a raw-string, product-prefixed, or cross-grammar placeholder. Revisit as a dedicated future API research task with SQL-first call-site examples, Swift naming/operator constraints, and downstream compatibility analysis.

4. **Pre-DESIGN-019 Duck retrospective cross-dialect audit** - CLOSED. The required retrospective audit of the pre-star/COLUMNS Duck foundation under current DESIGN-019 and DIALECT-014 is complete. Every mandated capability was independently classified as either `NO DESIGN-019 IMPACT` or `PASS`, with zero remaining `CORRECTION REQUIRED` items. Required corrections were completed and independently accepted for collision-safe structured render-scope identity, open hybrid representation keys, structured nested-type rendering independent of its legacy textual compatibility projection, open structured sampling with dialect-owned bind/parser-constant policy, semantic SQL-lambda representation, explicit ASOF condition-role structure, and lossless `QueryParts` materialization of stored join builders. PostgreSQL/MySQL SQL and bind compatibility plus downstream extension behavior were re-verified after the corrections, and the accepted Duck native/public closure remained green. This retrospective prerequisite is therefore satisfied; future shared dialect/rendering/preparation/composition changes remain subject to DESIGN-019 and DIALECT-014.

5. **Later Duck administration/runtime families remain deliberately deferred** - The first `.duck` closure is complete and includes the validated ordinary application/analytics/schema/catalog/file-function surface, but it intentionally does not claim the full DuckDB administration/runtime universe. INSTALL/LOAD, secret management, broad PRAGMA/configuration, CHECKPOINT, VACUUM/ANALYZE administration, variables, EXPORT/IMPORT DATABASE, SHOW/DESCRIBE/SUMMARIZE convenience, extension-specific SQL universes, and other unclassified administration/runtime families require separate typed research/UX/native-validation waves before becoming support claims. Their absence is not a blocker for the completed first closure.

6. **PostgreSQL TABLESAMPLE unit rendering is not PostgreSQL-correct** - The current shared `SwifQLPartSampling.renderedParts` appends `PERCENT` or `ROWS` when a TABLESAMPLE argument carries `.percentage` / `.rows` semantic roles. `PostgreSQLDialect` currently uses that default rendering unchanged. PostgreSQL 18 grammar is `TABLESAMPLE sampling_method ( argument [, ...] ) [ REPEATABLE ( seed ) ]`; its built-in `SYSTEM` / `BERNOULLI` methods interpret the argument as a percentage semantically but do not use a `PERCENT` keyword, and PostgreSQL has no generic `ROWS` unit in TABLESAMPLE grammar. DuckDB does use `PERCENT` / `ROWS` forms, so the existing semantic roles remain useful and the correction belongs in dialect-owned rendering rather than public API distortion. Closure requires exact PostgreSQL TABLESAMPLE tests for built-in and open/custom sampling methods, byte-for-byte Duck regression coverage, preserved bind/value observation semantics, and confirmation that MySQL remains unaffected/unsupported as appropriate.

7. **General PostgreSQL subscript bases are not parenthesized when required** - The established `SwifQLable` subscript implementation appends `[...]` directly to the receiver's parts. PostgreSQL 18 permits omitted parentheses only when the subscripted expression is a column reference or positional parameter; a general expression such as a function call requires parentheses, e.g. `(arrayfunction(a,b))[42]`. The current documented SwifQL source example `Fn.arrayAgg(...)[1]` therefore has a PostgreSQL correctness gap when it materializes as an unparenthesized function/aggregate expression. This debt is independent of future declarative ARRAY/slice authoring. Closure requires structural classification of subscript bases without rendered-token/text scanning, exact PostgreSQL positive coverage for column/parameter and parenthesized function/aggregate/complex-expression bases, preserved left-to-right binding order, and explicit Duck/MySQL compatibility classification before changing established output.

8. **`Fn.count()` does not represent all-row COUNT consistently across built-in dialects** - The public zero-argument helper is documented in source as returning the count of all rows but currently lowers through ordinary `Fn.build(.count, body: [])`, producing `count()`. DuckDB documents `count()` as an alias of `count(*)`, but PostgreSQL's aggregate grammar represents the no-input all-row form as `count(*)`, and MySQL documents `COUNT(*)` as the row-count form while `COUNT(expr)` counts non-NULL expression values. This is an existing exact-SQL compatibility defect, not permission for the declarative aggregate design to invent a replacement name. Closure requires a separately approved compatibility correction that preserves the useful `Fn.count()` source call if cleanly possible, emits correct all-row SQL for PostgreSQL/MySQL, preserves Duck behavior, and protects `count(expression)`, `count(DISTINCT ...)`, FILTER/OVER composition, and bind ordering with focused regression coverage.

9. **Fluent multi-predicate aggregate FILTER emits a comma list instead of one boolean expression** - The established `SwifQLable.filter(where: [SwifQLable])` implementation writes multiple predicates as `FILTER (WHERE p1, p2, ...)`. PostgreSQL aggregate/window grammar owns one `filter_clause` boolean expression inside `FILTER (WHERE ...)`; comma-separated predicates are not that grammar. DuckDB v1.5.5 native evidence independently confirms the same structural boundary: both `FILTER (WHERE predicate)` and Duck's accepted `FILTER (predicate)` form execute, while `FILTER (WHERE p1, p2)` is parser-rejected at the comma. The future declarative `Filter { ... }` design is already independently defined to combine surviving direct predicates with `AND`, so it must not inherit this historical output. Closure of the fluent defect requires a separate compatibility decision for the existing multi-argument API, exact PostgreSQL regression evidence for one and multiple predicates, explicit MySQL classification, preserved single-predicate output and binding order, and no change to the accepted declarative FILTER ownership merely to preserve malformed historical SQL.

10. **Legacy MySQL JSON path helpers render PostgreSQL function names without native MySQL semantics** - Existing SwifQL tests intentionally preserve historical MySQL rendering such as `json_extract_path(...)`, `json_extract_path_text(...)`, `jsonb_extract_path(...)`, and `jsonb_extract_path_text(...)`. PostgreSQL documents `json_extract_path` / `jsonb_extract_path` as native functions equivalent to its `#>` family, while MySQL 8.4 documents JSON extraction through its own `JSON_EXTRACT(...)` and `$`-based path language rather than those PostgreSQL function names. The current tests therefore establish render compatibility, not validated MySQL execution semantics. Expression Frontier 02 must not treat these historical helpers as a truthful cross-dialect JSON-path abstraction. Closure requires a separately approved compatibility investigation with native MySQL execution evidence, explicit migration/source-compatibility policy for the existing helpers, and a decision whether corrected MySQL-native APIs are additive, dialect-specific, or require a major-version behavior change.
