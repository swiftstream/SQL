# Project Memory

This file keeps durable, non-obvious current facts that are useful beyond immediate source inspection. Architecture rules remain in their owners.

- `Package.swift` defines a dependency-free Swift package with one `SQL` library target and one `SQLTests` test target.
- Production source is under `Sources/SQL`; tests are under `Tests/SQLTests`.
- The accepted Declarative DDL authoring surface is current source truth. SQL now owns generic SQL-only `CreateTable`, `AlterTable`, `AddColumn`, `TableDefinition`, `AlterTableAction`, and their dedicated restricted result builders. The DDL builders are intentionally non-empty/static: direct `if`, `if/else`, optional-binding branches, loops, unrelated `SQLable` children, and empty closures fail to compile. `CreateTable` snapshots child parts so later mutation of a `NewColumn` cannot rewrite an already-built statement; `AlterTable` always represents exactly one SQL ALTER TABLE statement and does not reuse the legacy `UpdateTableBuilder` routing state machine.
- Historical-schema-safe declarative DDL uses explicit string table/schema/column identifiers. Current model table names, property wrappers, and key paths must not rewrite old migration declarations. Existing general SQL model/key-path conveniences remain compatibility surface for non-migration/general DSL use.
- Declarative query result-builder authoring now uses DESIGN-037 fragment-first composition in committed production source. The final DESIGN-037 technical correction is commit `a50497ab4d78262032cc1b16224eec4fb78f6aae` (`🪚 Make query composition fragment-first`), exactly 122 paths = 117 production sources + 5 tests. `SQL { ... }` may represent complete SQL or reusable partial/non-executable fragments; standalone clauses and source-order permutations render faithfully, while whole-statement validity, clause ordering, and completeness belong to the target database/parser/driver. Specialized builders retain only local deterministic rendering/safety/ownership constraints. The former N01-N33 whole-statement compile-negative assumptions and guaranteed-FROM carrier model are historical; `GuaranteedFromBuilder` / `GuaranteedResult` and static source-existence/whole-order proof are removed. Final source/diff audit and staged-package audit were independently CLEAN, the canonical 119 tracked-candidate diff identity matched exactly, and the three new tests were separately exact. No universal mega-builder/parallel AST is approved. Query authoring remains SQL-first on the existing parts/preparation/binding pipeline. `SQLable` still refines `RowField`; downstream conditional `SQLable` conformers must restate `RowField` with matching bounds. L2 package import remains a limitation, not green.
- The local major-version public identity migration from `SwifQL` to `SQL` is complete through canonical source/API (`1eb1192227f500341243e7dab4690d6d72262b34`), package/module/path migration (`35afa7457eea8ac561e13319ca012ae4518ccce3`), and public documentation (`414b09a455e0058adb14e6f9f215134343880d86`); this governance synchronization records the final stable local state. The package/product/module is `SQL`, production is `Sources/SQL`, tests are `Tests/SQLTests`, `import SwifQL` is unsupported, and compatibility is symbol-level through deprecated/renamed declarations inside module `SQL`. The remote repository/public destination `github.com/swiftstream/SQL` remains planned only; no remote rename/publication has been performed by the local migration.
- Reusable SwiftUI-style parameterized query values via `SQLQuery` remain on the same SQLable/preparation architecture introduced by `616c45775cada4481da3fe2b704b921f675ac264` (`✨ Add reusable SQLQuery components`), with the pre-publication root/type correction now committed as `1f656ffe22404b2cdb39546ea3dcfdee7be6abc8` (“🛠 Restore direct `SQL` fluent root”). The public requirement is `@SQLBuilder var query: SQLValue { get }`; ordinary conformers write a plain `var query: SQLValue { ... }` witness because the builder transform is inherited from the requirement. `SQL` is the direct public fluent root/function spelling, `SQL { ... }` remains declarative construction, and `SQLValue` is the concrete fragment/result carrier. The default SQLable witness still forwards `parts` directly to `query.parts`; there is no static fluent-mirror family or parallel executor/repository/ORM/AST/renderer. The exact corrected candidate passed 737 tests / 63 suites on Swiftly 6.3.3, Xcode 26.6 Swift 6.3.3, and Xcode 27 Swift 6.4, plus the normal-import client matrix and 37/37 direct-root representatives. Public docs were synchronized in `6fd973e9a3edad075eb50ff4fbb52380bc4ca3ee` and managed query-building skills in `4558af69c7a99520ddb79374bae4ff877d726c1a`. `SQL.root` was an unreleased intermediate local spelling and is not compatibility surface.
- The source-owned downstream conversion skill `swifql-sql-conversion` is implemented and validated at `.agent/skills/swifql-sql-conversion/SKILL.md`; its S1 implementation commit is `3518edee9c12a29b6f55c94dc0fdb87ecd1c8ab9` (`📖 Add SQL conversion skill`). It targets the canonical `SQL` module/API, resolves the consumer's actual package version/source before conversion, uses only source/test-verified APIs, and never invents missing helpers. Unsupported typed/core syntax may fall back only to explicit static raw structure; dynamic or untrusted data must remain on the normal value/bind path. Every later accepted query-surface wave must impact-check this skill and update it only when canonical constructs or spellings change; `NO_CHANGE` is valid otherwise. Publication to the external `swiftstream/skills` collection remains a separate future wave and is not implied by this local source-owned checkpoint.
- PostgreSQL and MySQL are established dialects. The first Duck dialect closure is now implemented, native-/compatibility-validated, independently audited, and committed. Current source includes the validated ordinary application/analytics/schema Duck surface plus catalog/file-function support; later administration/runtime families remain deferred. SQL builds SQL only and does not execute DuckDB.
- The compact current pipeline is composable parts -> one shared preparation renderer -> `SQLPrepared` and formatter output. Ordinary `prepare(_:)` and additive `prepareObservingUnsafeValues(_:)` use that same selected render and bound-value collector; complete observation aligns each `bound(index)` to the exact prepared values slot, while semantic paths that cannot prove complete provenance fail closed as `.unavailable` without changing SQL/value output. See [`DSL_COMPOSITION.md`](architecture/DSL_COMPOSITION.md) and [`QUERY_PREPARATION.md`](architecture/QUERY_PREPARATION.md) for the owning contracts.
- [`DSL_DESIGN_AND_UX.md`](architecture/DSL_DESIGN_AND_UX.md) is the stable owner of the SQL-first public API mental model, API taxonomy, SQL transparency, convenience boundaries, reuse-before-abstraction rule, dialect-transparent user-facing DSL requirement, and new-API checklist. - Dialect documentation is split for context budget: [`DIALECT_RENDERING.md`](architecture/DIALECT_RENDERING.md) owns only cross-dialect rules, while [`dialects/DUCK.md`](architecture/dialects/DUCK.md), [`dialects/POSTGRES.md`](architecture/dialects/POSTGRES.md), and [`dialects/MYSQL.md`](architecture/dialects/MYSQL.md) own per-dialect facts. - Dialect-specific support does not automatically justify database-prefixed query APIs. Ordinary user source should name clean SQL concepts and let dialect-aware preparation own syntax differences whenever truthful. If a DuckDB-specific Swift implementation symbol genuinely needs a prefix, use `Duck...` / `duck...`, not new `DuckDB...` / `duckDB...` prefixes. The canonical public dialect API is `.duck`, so Duck preparation uses `prepare(.duck)`; reserve `"duckdb"` for internal database identity/prose. The completed first closure adds `.duck` to `SQLDialect.all`, which is now PostgreSQL + MySQL + Duck.
- The public library has a substantial historical PostgreSQL-specific surface; another dialect does not automatically make those helpers portable.
- The existing PostgreSQL implementation is the primary local style/organization reference for new dialect code, but target-dialect official documentation owns target SQL semantics.
- Canonical new Swift API uses SQL-shaped camelCase with position-aware abbreviation casing owned by `DESIGN-012`. True abbreviations are lowercase when leading and uppercase when medial (`jsonBuildArray` / `fromJSON`, `jsonbTypeOf` / `toJSONB`, `readCSV`, `toTSVector`, `concatWS`); `Id` is the explicit exception (`groupingId`, never `groupingID`). Ordinary shortened fragments such as `str` and `pos` are not abbreviations (`strPos`, `subStr`). Compound pieces are position-aware (`recordSet`/`RecordSet`, `regExp`/`RegExp`, `base64`/`Base64`). SQL-derived pieces are not translated into different English words (`nextval` -> `nextVal`, never `nextValue`). Current `readCSV` / `readJSON` spellings are canonical under this final rule. Established historical noncanonical spellings remain deprecated `renamed:` bridges when compatibility requires them, while unreleased intermediate mistakes are corrected directly.
- Existing PostgreSQL/MySQL query source, generated SQL, bind order, composition behavior, and downstream Swift extensions are compatibility contracts by default.
- The current Duck redesign has explicitly rejected cross-dialect semantic portability facades such as `binary(...)`: exact SQL functions remain exact APIs (`decode` stays `decode`; `from_base64` uses canonical Swift `Fn.fromBase64`, with only a deprecated snake_case bridge if the approved plan includes one). Dialect preparation may adapt the same construct's syntax/casing, not substitute a differently named construct.
