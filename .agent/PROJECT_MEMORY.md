# Project Memory

This file keeps durable, non-obvious current facts that are useful beyond immediate source inspection. Architecture rules remain in their owners.

- `Package.swift` defines a dependency-free Swift package with one `SwifQL` library target and one `SwifQLTests` test target.
- Production source is under `Sources/SwifQL`; tests are under `Tests/SwifQLTests`.
- The accepted Declarative DDL authoring surface is current source truth. SwifQL now owns generic SQL-only `CreateTable`, `AlterTable`, `AddColumn`, `TableDefinition`, `AlterTableAction`, and their dedicated restricted result builders. The DDL builders are intentionally non-empty/static: direct `if`, `if/else`, optional-binding branches, loops, unrelated `SwifQLable` children, and empty closures fail to compile. `CreateTable` snapshots child parts so later mutation of a `NewColumn` cannot rewrite an already-built statement; `AlterTable` always represents exactly one SQL ALTER TABLE statement and does not reuse the legacy `UpdateTableBuilder` routing state machine.
- Historical-schema-safe declarative DDL uses explicit string table/schema/column identifiers. Current model table names, property wrappers, and key paths must not rewrite old migration declarations. Existing general SwifQL model/key-path conveniences remain compatibility surface for non-migration/general DSL use.
- Declarative query result-builder authoring is the current maintainer-approved objective and is partially implemented (DQ-00..DQ-04 committed; sibling JOIN dual-form committed as `1982790`). The accepted static DDL builders do not pre-decide its runtime grammar and no universal mega-builder/parallel AST is approved. Query-authoring design stays SQL-first, reuses existing parts/preparation/binding, supports runtime control flow only where grammar permits omission, and shows exact Swift -> SQL for every accepted syntax. Sibling `Join` after a guaranteed completed `From` is equally supported to nested `Join` with identical SQL/binds (DESIGN-022/028).
- The final major-version public identity is planned to migrate from `SwifQL` to `SQL` after the declarative query-authoring capability is designed/created: final root spelling `SQL { ... }`, `SwifQLable -> SQLable`, reviewed corresponding `SwifQL...` renames, and repository/public package destination `github.com/swiftstream/SQL`. Current source/package/repository names remain `SwifQL` until that dedicated migration wave executes. This planned rename is an intentional major-version breaking migration and must carry explicit migration/compatibility/public-content records.
- Immediately after declarative result-builder query authoring, the roadmap includes reusable SwiftUI-style parameterized query values via a final `SQLQuery` protocol/pattern. The canonical target is a result-builder-attributed `query` protocol requirement so conformers can write clauses directly in `var query: SQL { Select { ... }; From { ... }; Where { ... } }` without a nested `SQL { ... }` wrapper. A conforming struct owns input state plus that declarative query body, prepares directly through the ordinary SQL pipeline, and is itself composable as a nested/subquery source without callers manually unwrapping `.query`. This must remain a reusable SQL-producing value, not an executor/repository/ORM or parallel AST. Final public naming should target `SQLQuery`; do not publish a temporary `SwifQLQuery` merely to rename it immediately afterward.
- PostgreSQL and MySQL are established dialects. The first Duck dialect closure is now implemented, native-/compatibility-validated, independently audited, and committed. Current source includes the validated ordinary application/analytics/schema Duck surface plus catalog/file-function support; later administration/runtime families remain deferred. SwifQL builds SQL only and does not execute DuckDB.
- The compact current pipeline is composable parts -> one shared preparation renderer -> `SwifQLPrepared` and formatter output. Ordinary `prepare(_:)` and additive `prepareObservingUnsafeValues(_:)` use that same selected render and bound-value collector; complete observation aligns each `bound(index)` to the exact prepared values slot, while semantic paths that cannot prove complete provenance fail closed as `.unavailable` without changing SQL/value output. See [`DSL_COMPOSITION.md`](architecture/DSL_COMPOSITION.md) and [`QUERY_PREPARATION.md`](architecture/QUERY_PREPARATION.md) for the owning contracts.
- [`DSL_DESIGN_AND_UX.md`](architecture/DSL_DESIGN_AND_UX.md) is the stable owner of the SQL-first public API mental model, API taxonomy, SQL transparency, convenience boundaries, reuse-before-abstraction rule, dialect-transparent user-facing DSL requirement, and new-API checklist. Agents should load it instead of rediscovering these principles from source.
- Dialect documentation is split for context budget: [`DIALECT_RENDERING.md`](architecture/DIALECT_RENDERING.md) owns only cross-dialect rules, while [`dialects/DUCK.md`](architecture/dialects/DUCK.md), [`dialects/POSTGRES.md`](architecture/dialects/POSTGRES.md), and [`dialects/MYSQL.md`](architecture/dialects/MYSQL.md) own per-dialect facts. Load only the relevant dialect owner by default.
- Dialect-specific support does not automatically justify database-prefixed query APIs. Ordinary user source should name clean SQL concepts and let dialect-aware preparation own syntax differences whenever truthful. If a DuckDB-specific Swift implementation symbol genuinely needs a prefix, use `Duck...` / `duck...`, not new `DuckDB...` / `duckDB...` prefixes. The canonical public dialect API is `.duck`, so Duck preparation uses `prepare(.duck)`; reserve `"duckdb"` for internal database identity/prose. The completed first closure adds `.duck` to `SQLDialect.all`, which is now PostgreSQL + MySQL + Duck.
- The public library has a substantial historical PostgreSQL-specific surface; another dialect does not automatically make those helpers portable.
- The existing PostgreSQL implementation is the primary local style/organization reference for new dialect code, but target-dialect official documentation owns target SQL semantics.
- Canonical new Swift API uses SQL-shaped camelCase with position-aware abbreviation casing owned by `DESIGN-012`. True abbreviations are lowercase when leading and uppercase when medial (`jsonBuildArray` / `fromJSON`, `jsonbTypeOf` / `toJSONB`, `readCSV`, `toTSVector`, `concatWS`); `Id` is the explicit exception (`groupingId`, never `groupingID`). Ordinary shortened fragments such as `str` and `pos` are not abbreviations (`strPos`, `subStr`). Compound pieces are position-aware (`recordSet`/`RecordSet`, `regExp`/`RegExp`, `base64`/`Base64`). SQL-derived pieces are not translated into different English words (`nextval` -> `nextVal`, never `nextValue`). Current `readCSV` / `readJSON` spellings are canonical under this final rule. Established historical noncanonical spellings remain deprecated `renamed:` bridges when compatibility requires them, while unreleased intermediate mistakes are corrected directly.
- Existing PostgreSQL/MySQL query source, generated SQL, bind order, composition behavior, and downstream Swift extensions are compatibility contracts by default.
- The current Duck redesign has explicitly rejected cross-dialect semantic portability facades such as `binary(...)`: exact SQL functions remain exact APIs (`decode` stays `decode`; `from_base64` uses canonical Swift `Fn.fromBase64`, with only a deprecated snake_case bridge if the approved plan includes one). Dialect preparation may adapt the same construct's syntax/casing, not substitute a differently named construct.
- Gate A bounded semantic render scopes and Gate B structural clause ownership are evidence-proven. The accepted major-version Gate B architecture uses generic value-semantic SQL-region/set-result root frames to select open clause ownership through one generic root-frame-aware continuation primitive; dedicated owner-sensitive clauses persist that owner inside `parts`; nested frames isolate statement-local scopes while one renderer/binding collector traverses the structural tree. The disposable diagnostic passed the exact erased PIVOT source, 20/20 structural matrix, byte-for-byte PostgreSQL/MySQL compatibility matrix, QueryParts/builders, raw/`~` semantics, copied `parts`, binding order, and external custom owner/kind/dialect/scope consumer. `PIVOT-CLAUSE-OWNERSHIP-001` is closed. Focused semantic-statement/full-AST routing remains unapproved.
- The complete Duck implementation-plan/audit lineage and first closure are complete. The final closure sequence preserved `.all` as PostgreSQL/MySQL through compatibility classification, then added `.duck` only after the native/public gates passed, followed by full post-mutation verification. The structural SQL-region model, PIVOT/UNPIVOT/MERGE and approved first-closure surface are current production source. PIVOT GROUP BY keeps erased generic `.groupBy(SwifQLable...)`; there is no fake PIVOT-only `KeyPathLastPath` overload, and `KeyPathLastPath` remains public compatibility surface for APIs that can truthfully own a column-name-only static grammar.
- The package uses SwiftPM tools 6.3 in Swift 6 language mode (`swift-tools-version: 6.3`, `swiftLanguageModes: [.v6]`). Release CI validates with Apple Swift 6.3.3 while intentionally preserving non-Sendable query/bind graphs. Canonical predefined `Fn.Name` values are immutable; custom names remain available through `Fn.Name.custom(_:)` / `Fn.build(_:)`.
- The completed first SwifQL 2 Duck/Swift-6 closure is published as pre-release `2.0.0-beta.5.0.0`. The canonical GitHub repository is `https://github.com/SwifQL/SwifQL`; current public package examples use the `SwifQL` organization and omit unnecessary `.git` suffixes. Final stable `2.0.0` remains a distinct future release state unless explicitly published later.
- The shared semantic values `PureDate`, `PureTime`, `DateTime`, and `Interval` were first published in `2.0.0-beta.6.0.0`; `2.0.0-beta.6.0.1` is the immutable Swift 6.3 tools/CI compatibility hotfix. The current release candidate/current prerelease is `2.0.0-beta.6.1.0`, which adds the accepted Declarative DDL authoring surface under semantic source filenames. Downstream repositories must still perform their own exact dependency-handoff and remote-resolution validation.
- `PureDate` and `PureTime` map automatically to `.date` and `.time`; `Foundation.Date` remains `.timestamptz`; `DateTime` and `Interval` retain the historical `.text` inference fallback and use explicit schema types when timestamp/interval semantics are intended. The four values use the ordinary one-pass unsafe-value preparation path and preserve dynamic Swift values in collector order.
